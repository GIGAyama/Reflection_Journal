# Driveネイティブ版の設計と検証手順

## 目的

Firebase、学校ごとのGASデプロイ、運営者アカウント経由のデータ書き込みを使わず、次を満たす。

- 入口は既存のGitHub Pages共通URLのまま
- 先生も児童もGoogleアカウントでログインするだけ
- 成果物は児童自身のGoogle Driveに保存する
- 児童から担任へ、Google Driveの標準共有で直接渡す
- 担任はクラス別に共有済み成果物を一覧表示する
- 利用者はGASやGoogle Cloudをデプロイしない

## データの流れ

```text
GitHub Pages（画面 + GIS OAuth）
  ├─ 先生のDrive
  │    └─ クラス設定JSON（先生が所有）
  └─ 児童のDrive
       ├─ ポートフォリオJSON（児童が所有、担任へ閲覧共有）
       └─ 添付画像（児童が所有、担任へ閲覧共有）
```

運営者のGoogleアカウントはデータの所有者にも共有先にもならない。学校のドメイン内で許可される「児童→担任」の共有だけを使うため、従来の「運営者アカウント→学校所有シート」へのアクセス制限を受けない。

## 権限境界

- OAuthスコープは `drive.file`。アプリが作成したファイルまたは利用者がアプリで選択したファイルだけを扱う。
- アクセストークンはメモリ内だけに保持し、`localStorage`、`sessionStorage`、Cookieへ保存しない。
- ポートフォリオと画像は担任メールアドレスへ `reader` として直接共有する。
- 共有メールは毎回送らず、アプリ画面で一覧化する。
- 招待URLにはクラス名・コード・担任名・担任メールだけをURLフラグメントとして含める。アクセストークンやDriveファイルIDは含めないため、Webサーバーのアクセスログへ送られない。
- クラスIDは正規化済みの担任メールとランダムなクラスコードのSHA-256から決定する。中央レジストリは置かない。

## ファイル形式

### クラス設定

- MIME: `application/json`
- 所有者: 担任
- `appProperties`: `rjType=class`, `rjClassId`, `rjSchema=1`
- 内容: クラス名、コード、クラスID、担任情報、作成・更新日時

### 児童ポートフォリオ

- MIME: `application/json`
- 所有者: 児童
- 共有先: 担任（閲覧者）
- `appProperties`: `rjType=portfolio`, `rjClassId`, `rjSchema=1`
- 内容: 児童情報、クラス情報、ふりかえり配列

1投稿1ファイルにはしない。児童1人・1クラスにつきポートフォリオ1ファイルとし、担任の「共有アイテム」を増やしすぎない。添付画像だけはバイナリの別ファイルにする。

## 移行スイッチ

現在は `docs/config.js` の `backendMode` を `gas` にしており、現行版を既定のまま残している。

- 担任の検証入口: 共通URLに `?backend=drive` を付ける
- Drive版の招待URL: 共通URLの `#join=...`（自動でDrive版へ移動）
- 本番切替: 実アカウント検証後、`backendMode: "drive"` に変更
- ロールバック: `backendMode: "gas"` に戻す

## 運営者が一度だけ行う設定

利用者ごとのデプロイは不要。ただし、共通のOAuthクライアントを管理する運営者は次を一度だけ行う。

1. 現在のOAuthクライアントが属するGoogle CloudプロジェクトでGoogle Drive APIを有効化する。
2. OAuthウェブクライアントの承認済みJavaScript生成元に `https://gigayama.github.io` があることを確認する。
3. OAuth同意画面へ `drive.file` の利用目的、プライバシーポリシー、サポート連絡先を記載する。
4. 学校の管理者が18歳未満ユーザーの未構成サードパーティアプリを制限している場合、OAuthクライアントIDを信頼済みアプリとして許可してもらう。

4はGoogle Workspaceの管理ポリシーであり、アプリ側から回避してはいけない。許可後も学校ごとのGASデプロイは発生しない。

## 実アカウント受け入れテスト

自動テストはAPI要求形式とデータ変換を確認する。Google側の組織ポリシーは実アカウントで次を確認する。

1. 個人アカウントの担任役で `?backend=drive` を開き、クラスを作る。
2. 別の個人アカウントでQRまたは専用URLを開き、参加して本文と画像を保存する。
3. 担任役でクラスを再表示し、児童名・本文・画像が見えることを確認する。
4. 同じ学校ドメインの担任・児童アカウントで1〜3を行う。
5. 学校の共有制限下で失敗した場合、白画面ではなく「Workspace設定を確認」の案内と「先生へ再共有」が表示されることを確認する。
6. ブラウザを閉じて再度開いたとき、トークンが残らず再ログインになり、Drive上の参加済みクラスは復元されることを確認する。

特に、同じOAuthクライアントで児童が作成・共有した `appProperties` 付きファイルを、担任の `drive.file` トークンで `sharedWithMe` 検索できることを個人・学校アカウントの両方で確認してから既定を切り替える。

## 現段階の制限

- この移行版で実装済みなのは、クラス作成、URL/QR招待、参加、本文・気持ち・画像保存、担任一覧・閲覧。
- 担任から児童へのコメント返却、テーマ配信、分析、CSV、既存スプレッドシートからの移行は次段階。現行GAS版はそのため残している。
- 学校が児童から担任へのDrive共有そのものを禁止している場合、この方式でも共有はできない。これはデータ保護ポリシーとして尊重し、管理者の許可または学校が認める保存先が必要。
- 異なるドメイン間の共有は両側の管理ポリシーに従う。同一学校ドメインでの利用を基本とする。
- URLだけでは中央レジストリを使わないため、コード単独参加では担任メールアドレスとクラス名も必要。通常はQRまたは専用URLを使う。
