# Driveネイティブ設計

## 設計目標

- GitHub Pagesの共通URLだけを入口にする。
- Firebase、共通サーバー、中央データベース、学校別GASを使わない。
- 児童と先生がそれぞれ自分の成果物を所有する。
- 利用者にデプロイやスプレッドシート共有設定をさせない。
- 学校ドメインのポリシーを回避せず、拒否時は理由を画面に示す。

## ファイルと所有権

| 種別 | 所有者 | 共有先 | 内容 |
| --- | --- | --- | --- |
| class | 先生 | 共有しない | 設定、名簿、参加状態、Geminiキー |
| portfolio | 児童 | 先生（reader） | 本文、気持ち、画像ID、過去コメント |
| journal-image | 児童 | 先生（reader） | 縮小済み添付画像 |
| channel | 先生 | 対象児童（reader） | テーマ、承認状態、コメント、スタンプ |

提出と返却を別ファイルにすることで、児童と先生が同じJSONを同時更新して上書きする競合を避ける。先生は児童本文を変更できず、児童は先生の返却を変更できない。

## 検索

各ファイルへDriveの `appProperties` を付ける。

- `rjSchema=2`
- `rjType=class|portfolio|channel|journal-image`
- `rjClassId=<SHA-256>`
- チャンネルのみ `rjStudent=<児童メールのSHA-256>`

クラスIDは先生メールとランダムな8文字コードから決定的に生成する。招待情報はクラスごとに生成するECDSA P-256鍵で署名し、有効期限・発行世代・公開鍵IDを含める。URLフラグメントへBase64URLで格納するため、GitHub Pagesや中継サーバーのアクセスログへは送信されない。秘密鍵は先生所有の非共有classファイルにだけ保存する。

## OAuth

- GIS token modelを使用する。
- 最初のトークン要求は `openid email profile drive.file` だけとする。
- 先生／児童の共有記録同期を開始する直前に、`drive.readonly` がDrive全体の閲覧を許可する制限付きスコープであることを説明し、段階的に要求する。
- 自分の専用ファイルの作成・更新・共有は `drive.file`、別ユーザーから共有されたportfolio/channel/画像の検索・読込みは `drive.readonly` を使う。
- `drive.readonly` でDrive全体の閲覧権限が付与されるが、実装は `sharedWithMe` と `rjType` / `rjClassId` の一致する専用ファイルだけを取得する。
- 既定でアクセストークンはJavaScriptメモリにだけ置き、`sessionStorage`、`localStorage`、Cookieへ認証情報を保存しない。これは共有GitHub Pagesオリジンに同居する他アプリからのトークン取得リスクを下げるためである。
- 児童の未提出下書きはページのメモリだけに保持し、`localStorage` へ保存しない。旧版の `rj_draft_v2_` キーは起動時に削除する。`localStorage` には既読状態、前回の役割・クラスIDだけを保存する。

## 参加フロー

1. 先生がクラスを作り、専用URL／QRを配る。
2. 児童がポートフォリオを自分のDriveへ作り、先生へreader共有する。
3. 先生アプリが認可済みの読取許可を使い、`sharedWithMe` からポートフォリオを見つける。
4. 承認時、先生が児童別チャンネルを作って児童へreader共有する。
5. 以後、児童はポートフォリオを更新し、先生はチャンネルを更新する。

教師側は共有ポートフォリオを名簿へ取り込む前に、JSON内の児童メールとDrive所有者、クラスID、先生メール、署名付き招待の鍵IDと発行世代を検証する。児童側もチャンネル内の先生メールとDrive所有者を照合する。

## 競合・同期・保全

- JSON更新前にDriveの `version` を取得し、画面が読んだ版と異なる場合は上書きせず再読込みを求める。これはDrive API上のバージョン照合によるベストエフォートの楽観的競合検知である。
- ファイルID、`modifiedTime`、`version` が同じJSONはメモリキャッシュから再利用し、30秒更新時の本文再取得を抑える。
- 先生は手動で、検証済みクラスJSON・ポートフォリオ・チャンネル・読取り可能な共有画像の複製とmanifestを自分のDriveフォルダへ作成できる。運営者のサーバーへは送信しない。

## 制約

- 学校が児童→先生、先生→児童のDrive共有を禁止している場合は利用できない。管理者が学校の規則に沿って共有を許可する必要がある。
- `drive.readonly` はGoogleの制限付きスコープである。運営者は外部公開前にOAuth審査を完了し、Googleの判定に応じてセキュリティ評価へ対応する。
- 18歳未満ユーザーや制限付きスコープの制限は回避しない。Workspace管理者が共通OAuthクライアントIDと利用スコープを信頼済みとして許可する。
- 中央レジストリがないため、クラスコード単独の検索は行わない。専用URLまたはQRを利用する。
- `drive.file` のファイル認可はユーザーごとのファイル単位であり、Drive共有だけでは別ユーザー側のアプリ認可にならない。このため共有データの自動同期を `drive.file` だけで実装しない。
- 先生がDriveからクラス設定やチャンネルを直接削除した場合、アプリは復元できない。Driveのゴミ箱から復元する。

## Gemini API

Geminiは任意機能。APIキーは先生所有の非共有classファイルへ平文保存するため、Google Cloud側でAPIと本番オリジンの制限を設定する。児童本文の送信について学校の承認を得たことを先生が明示しない限り、API呼出しを拒否する。生成結果は未確定の下書きとして画面へ入り、先生が確認して返却する。

## 実アカウント受け入れテスト

1. 個人アカウント2つで作成・参加・承認・提出・画像・返却を確認する。
2. 同一学校ドメインの先生・児童アカウントで同じ経路を確認する。
3. 最初は `drive.file` だけが要求され、役割選択後に `drive.readonly` の説明と追加認可が行われること、その後 `sharedWithMe` と `appProperties` の検索結果を両者で取得できることを確認する。
4. 共有を禁止したテスト環境で、403の説明と再共有UIを確認する。
5. 複数児童の同時提出中に、教師返却が児童ポートフォリオを上書きしないことを確認する。
6. 再読込み後は再ログインが求められ、ブラウザの保存領域にアクセストークンが残らないことを確認する。
